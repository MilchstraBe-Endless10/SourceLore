## TD-001 — tests/runtime/test_concurrency.py 偶发 UNIQUE 冲突

- **登记日期**：2026-11-25
- **状态**：已登记，暂不修复（本轮明确不修改该测试）
- **现象**：`tests/runtime/test_concurrency.py` 偶发 `UNIQUE constraint failed: meta.k`；表现为全部 103 个测试文件逐项 OK，但整体退出码为 1。
- **已知出现**：beta.3 Release CI run `45429491915`；D3 测试修复 commit `a001d7a` 的 CI run `45621430877`；本机复现约 1/3 概率。
- **归属判定**：beta.3 时期即存在，与 D3 跨来源绑定改动无关，属 flaky 测试。
- **未确认根因**：`meta.k` 唯一键在多进程并发写入 checkpoint 时被重复插入，疑在 `src/runtime/checkpoint_store.py` 的 CAS/写入路径；尚未定位，故本轮不动。
- **现行缓解**：按既有做法 `gh run rerun` 重试，`45621430877` 重跑后 conclusion=success。
- **后续建议**：独立排期，排查并发写入去重/重试逻辑，修复后以连续多次 CI 稳定通过为准，不再依赖 rerun。

## TD-002 — 静态模块关系（relation）检索覆盖不足

- **登记日期**：2026-11-25
- **状态**：已登记，PARTIAL，暂不修复
- **现象**：`query <github_id> --type relation` 返回 `state=NO_RELATIONS`。GitHub 根层快照未捕获静态模块关系；本地补充来源也未生成可回查的 relation 记录。AST 产物有 47 符号 / 153 导入 / 200 facts，但没有据此落成 relation 资产。
- **影响**：不能把 `NO_RELATIONS` 解释为"已验证该仓库无模块关系"；这是覆盖缺口，不是否定结论。P2 的深度理解能力需补这一环。
- **后续建议**：在 P2 中明确 relation 抽取、持久化与查询链路；要么从 AST 导入关系生成 relation 资产，要么在查询层明确区分"未采集"与"无关系"。

## TD-003 — 来源验证边界（本地真实性 / Fork 区分 / 第三方授权）

- **登记日期**：2026-11-25
- **状态**：已登记，边界声明，暂不扩大
- **已解决范围**：D3 完成"来源内容对应关系"验证——权威 `subject_record`（数字 ID + `resolved_repository`）+ 固定 Commit/Root Tree + GitHub 根层 blob_ref 是本地 blob map 的哈希一致子集；反例（伪造数字 ID、本地 ID 伪装、无权威记录、blob 冲突）均被拒。
- **未解决边界**：本地来源真实性、Fork 区分、第三方内容授权边界**未全面解决**。验证依赖现有 A 层权威记录，未做独立的远端/链上身份二次认证，也未对第三方内容授权做新的法律判定。
- **影响**：不得把"内容对应验证通过"升格为"跨仓库身份与授权已全面可信"。跨来源门禁仍需保留人为裁决。
- **后续建议**：在后续阶段单独设计 Fork 区分（如远端签名/多源交叉）与授权边界机制，不得借 D3 通过之名放宽门禁。

## TD-004 — 宿主端到端自动触发与轨迹导出缺失

- **登记日期**：2026-11-25
- **状态**：已登记，宿主侧限制
- **现象**：已确认 SourceLore Skill 在宿主安装/启用，可手动读取；但宿主无调用轨迹导出工具，无法保存"真实 Skill 自动发现并端到端触发"的完整证据。
- **影响**：宿主端到端触发属于"未完成"，只能标记，不能用手动 `read_local_skill` 冒充自动触发成功。
- **后续建议**：待宿主提供轨迹导出能力后补验；在此之前该项在功能验收中保持未完成。
