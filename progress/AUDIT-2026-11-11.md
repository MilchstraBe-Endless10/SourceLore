# 【阶段 2 追加】阻断性发现：采集层从未保存正文

## 事实（直接查库所得）

`captured_blob_content` 共 7 条，**每条都只有元数据，没有正文字节**：

| 仓库 | 文件 | copy_permitted | raw_byte_length | 正文字节 |
|---|---|---|---|---|
| 24313173 | README.md | **False** | 6514 | 0 |
| 24313173 | index.js | **False** | 411 | 0 |
| 24313173 | package.json | **False** | 1599 | 0 |
| 38923193 | index.js | False | 344 | 0 |
| 38923193 | license | False | 1117 | 0 |
| 38923193 | package.json | False | 758 | 0 |
| 38923193 | readme.md | False | 794 | 0 |

字段清单（完整）：
`raw_byte_length` 有值、`content_sha256` 有值、`git_blob_oid` 有值
—— 但**没有任何 `text` / `content` 正文字段**。
且 `copy_permitted=False`、`distribution_allowed=False`。

## 结论

1. **采集层按授权策略刻意不保存正文**（`copy_permitted=false` 时只记元数据+哈希）。
   这个设计本身是合理的——它保护了来源授权。
2. 但直接后果是：**在现有数据上无法生成任何有真实内容的项目知识文档**。
   我写的 `repo_miner.py` 已正确识别这一点，如实输出「未采集正文，不得据此推断」。
3. 用户要求的「在 Bot 中阅读项目完整知识文档」，
   **在 `copy_permitted=false` 的前提下，按现有授权契约无法达成。**

## 这是产品级决策，不是技术选择

三条互斥路径：

**A. 放宽采集授权的适用范围**
   让 `copy_permitted` 在「本地内部使用」场景下可为 true，从而保存正文。
   需要确认：授权契约里 `copy_permitted` 的定义是否允许本地内部派生。
   风险：可能违反来源许可。

**B. 只保存派生摘要，不留原文**
   采集时立即提取结构化事实（标题、依赖名、脚本名、函数签名），
   原文读完即弃、不落库。文档由这些结构化事实生成。
   优点：不落原文，授权风险低。
   风险：仍需要能读取原文（网络+授权）。

**C. 保持现状，文档只陈述「可证明的元数据」**
   即当前状态：文件存在、大小、哈希、依赖声明、符号名。
   无法提供项目用途、架构说明等需要读正文的章节。
