## 3. Markdown 生成八问（D-A … D-H）

### D-A 不同知识类型提供哪些基础呈现视图
四类：完整报告（跨 Subject 综合）、摘要视图（一页概览）、单条 Subject 卡片、导航索引。
四类共享同一事实源，布局各自独立（c26 校验「不得出现不同数值」）。

### D-B 如何按受众控制信息密度
三档画像（决策者 / 维护者 / 审计者）× 三个可调参数（展开深度、证据可见度、术语密度）。
**唯一不可省略的四项**：结论、确认等级、覆盖缺口、生成快照。这是视图的最小完整性。

### D-C 完整报告、摘要、单条卡片如何共享同一份事实来源
同一 `authoritative_bundle` 派生，各自记录 `source_snapshot`。
同一事实在不同视图里不得出现不同数值——出现即判渲染错误。

### D-D 如何展示未验证的推断与 Unknown
按 `claim_type` 与 `validation_status` 四分呈现：fact（事实陈述）、declaration（标注为声明）、
inference（标注为推断，不得用肯定语气）、unknown（呈现为未知并说明缺什么）。
`insufficient` / `conflict` / 等待重验证 / `detection_incomplete` 必须在正文可见位置呈现状态。

### D-E 如何展示来源覆盖缺口与调查限制
覆盖缺口必须作为独立区块呈现（`coverage_gap`），不得并入「已知限制」笼统带过。
`partial` 视图必须在显眼处标 `partial`；`facts_only` 必须在开头自述「只有事实、没有解释性结论」。

### D-F 是否允许生成图表
允许，但由数据触发，不是门禁。详见第 5 节。

### D-G 如何避免整仓报告过长、无重点、重复展开底层细节
三层截断：视图层按受众密度裁剪；内容层同一底层细节只展开一次（其余引用引用 ID）；
导航层只给链接不给内容。硬规则：**同一底层细节在一个视图内不得重复展开超过一次**。

### D-H 生成失败时是否可保留上一份有效视图
可以，且必须。局部失败保留上一份有效版本，同时在生成清单标注该项 `failed`，
使「有清单但某页是旧的」可被察觉（c21 校验）。不得用半成品替换。

## 4. 知识卡片呈现

卡片是结构化知识资产的**派生视图**，至少呈现：`subject_id`、标题与摘要、内容类别、
来源仓库与固定版本、对应 Claim ID、Evidence 引用、验证结果、知识新鲜度、已知限制、生成时间。

这些是**显示需求**，不代表 Renderer 拥有相关字段的定义权——字段定义归各自的上游模块。

三条不可越线（c25 校验）：
- **卡片不是 Claim 的第二份权威副本**。所有内容从上游权威数据派生。
- 不得在卡片里创造未经验证的新主张；发现需要新主张时回到上游产出 claim 候选。
- 卡片可以被重新生成，但不得覆盖不可变的历史 Claim 或 Evidence。

## 5. 图表能力裁决

**保留 U02-C17 的原始 REJECT 证据，但处置改为 REIMPLEMENT。**
要拒绝的是**强制出图机制**（模板固定 4 节点 flowchart、与实际架构无关也照画），
不是拒绝图表功能本身。混为一谈会导致连「有真实关系时画个图」都不敢做。

三条硬规则（c24 校验）：
1. 无法可靠提取关系时不生成图表——不得为凑「有架构图」而编造节点或边。
2. 每个节点与每条边必须指向上游数据项（entity / flow_evidence / relation），无来源的视觉元素不得出现。
3. 图表不是完成判据——缺图不构成报告不完整。

图表格式（Mermaid / SVG / 其他）属实现选择，不在本能力内锁定。

## 6. 自动生成与人工内容隔离

| 问题 | 裁决 |
|---|---|
| 自动生成文件放置位置 | 独立命名空间（候选约定 `_generated/`，正式契约待 F2） |
| 人工与生成如何分离 | **写侧代码不得提供指向人工维护目录的分支**——结构约束，不是流程提醒 |
| 自动生成标识如何记录 | `auto_generated` + 生成器名与版本 + run_id + source_snapshot + 生成时间 |
| 重生成允许覆盖什么 | 只允许覆盖同一命名空间内的旧生成产物 |
| 哪些文档必须人工审阅 | 待 F1-C（清单未定） |
| 如何避免覆盖人工解释 | 人工维护文档永不被覆盖，即使内容看起来过时 |
| 局部生成失败如何处理 | 保留上一份有效版本并标注 `failed` |
| 内容与权威版本如何绑定 | 每个产物记录 `source_snapshot`；版本不一致的产物不得与新产物混排而不加标注 |

**Renderer 不得覆盖 Lifecycle 的不可变历史记录**（c20 校验）。
原子写入与文件锁归 Storage，本条只定义「哪些文件可被覆盖」的语义边界。

## 7. 引用与结论呈现（两条零来源条目的理由）

`SL-CAP-0060` 与 `SL-CAP-0061` 无上游来源。说明写在此处以免误读：

- `U02-C16`（内联引用规则）已由 Research 的 `SL-CAP-0039` 承接；本条与它的关系是
  「0039 定义引用约束、本条定义呈现忠实度」，属跨模块依赖而非重复占用。
- `U02-C13` 归 Research 的 `SL-CAP-0038`（质量三态），本条只消费其状态值。
- `U05-C20` / `U06-C17`（分级与打码）归 Security 的 `SL-CAP-0053`；本条是它在渲染侧的执行面。
- `U05-C06`（Auto-generated 头）归 EC 的 `SL-CAP-0025`；本条的空间隔离由 `SL-CAP-0058` 承担。

剩下的内容（有引用不等于支持、状态必须显式、facts_only 不得冒充完整报告、禁止视觉掩盖、
禁止未校准百分比、不得提高确认等级、Markdown/HTML 转义、链接协议白名单、远程资源限制、
上游文本不得控流程、三级门禁互不推导、AI 不得自批 approved）是六源中没有任何一处
写成渲染侧契约的自建内容，属零来源独立设计。

**引用与结论六条纪律（c23 校验）：**
R-1 有引用不等于引用支持结论（支持关系归 EC，Renderer 只校验链接完整性）；
R-2 状态必须在正文可见位置呈现；R-3 禁止把 facts_only 渲染成完整研究报告；
R-4 禁止视觉样式掩盖数据缺失；R-5 禁止未校准百分比；
R-6 不允许 Renderer 私自提高任何结论的确认等级。

## 8. 呈现安全与发布门禁

**四类安全处理（c30 校验）：**
S-1 转义：Markdown 特殊字符、HTML/JS 注入防护、不可信链接校验（协议白名单）、
外部图片与远程资源限制（默认不加载）；S-2 脱敏检查（发现即阻断该片段，不先渲染再补救）；
S-3 上游文本不得控制渲染器执行指令；S-4 未经许可不得嵌入上游大段原始代码或受保护文本。

**三级门禁互不推导（c22 校验）：**

| 门 | 状态 | 谁能触发 |
|---|---|---|
| G-1 | 生成完成（产物已写出） | 机器 |
| G-2 | 安全检查通过（S-1..S-4 全过） | 机器 |
| G-3 | 发布授权（`approved_for_release`） | **只能是人** |

硬规则：自动生成完成 ≠ 脱敏通过；脱敏通过 ≠ 获得发布授权。
AI 可以标记 `pending_review`，但**不得自行触发仅允许人类执行的 approved 状态转换**。
Renderer 执行发布前检查，但发布权限定义归 Security 与 EC，实际访问控制由 Storage 与部署层落实。

## 9. 与 Storage 的边界

Renderer 可以请求：生成派生文档、生成卡片内容、生成导航视图、生成可检索展示文本。

它**不负责**：分配 Subject 身份、管理唯一知识登记表、实施文件锁与事务、维护权威索引、
删除或改写历史证据、决定知识是否已过期。

索引是否需要重建由 Lifecycle 与 Storage 的契约共同决定。Renderer 提供索引的**展示内容**，
但展示层不得成为权威索引数据的唯一来源（c48 校验）。

## 11. 本轮修掉的问题

### 定义文件自身（一处真实错误）

初版在 `SL-CAP-0055` 的 refs 里同时写了 `U01-C10` 与 `U02-C13`，但后者已由 Research 的
`SL-CAP-0038` 正式承接——同一原始身份只能映射一次。已从 refs 移除，改为在 notes 与本文档中
声明为「跨模块依赖」，引用数从 12 降到 11，与承接声明完全一致。

另修一处语法错误：`DEFERRED_TO_OTHER_MODULE` 里误写 `("UPSTREAM-03","C16").__class__ and (...)`，
属我的笔误，已改为正常键。

### 既有验证器作用域过时（两处，非数据缺陷）

1. **Research c15/c45** —— 出向计数要求 `redirected == 3`，但本批合法承接 `U02-C17` 后降为 2；
   c45 又要求该分流仍在路由表。两处均改为「与现算自洽」或「要么仍在路由表、要么已被预期目标承接」。
2. **Lifecycle c47** —— 全局检查「任何 owner=Lifecycle 的分流都判指向自身」。但后续批次
   （本批的 `U04-C16`、`U05-C10`）合法推入新身份给 Lifecycle 属正常职责裁决。
   已收窄为「只查本批 def 自己声明的那批」。

三处均只修正时间作用域与检查范围，未放宽身份唯一性、三态守恒、许可隔离等核心不变量。
